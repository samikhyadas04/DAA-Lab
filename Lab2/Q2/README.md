# Modified (3-Way) Merge Sort vs Standard Merge Sort

This project analyzes and empirically validates the worst-case running time
of a **3-way merge sort**: instead of splitting the input into halves, it is
split into thirds, each third is sorted recursively, and the three sorted
thirds are combined with a 3-way merge subroutine.

## 1. Theoretical analysis

**Recurrence.** Splitting into 3 equal parts of size `n/3`, sorting each
recursively, and merging three sorted runs of total length `n` takes linear
time (advancing through three pointers, always moving whichever holds the
current minimum, is `O(n)` work with a slightly larger constant than a 2-way
merge since each output element may require up to 2 comparisons instead of
1). So:

```
T(n) = 3T(n/3) + Θ(n)
```

**Master theorem.** Here `a = 3`, `b = 3`, `f(n) = Θ(n)`.

```
n^(log_b a) = n^(log_3 3) = n^1 = n
```

Since `f(n) = Θ(n^(log_b a))`, this is **Case 2** of the Master theorem, so:

```
T(n) = Θ(n log n)
```

**Conclusion:** the 3-way merge sort has the *same asymptotic worst-case
running time*, `Θ(n log n)`, as the standard 2-way merge sort. Splitting
into more pieces reduces the recursion depth (`log₃ n` vs `log₂ n`), but
each level's merge step does more comparisons (a 3-way merge needs up to 2
comparisons per element placed, vs. 1 for a 2-way merge), and these two
effects cancel out asymptotically — only the constant factor changes, not
the order of growth. Because of the extra comparisons per merge and the
overhead of managing three sub-arrays, the 3-way version is typically
*slightly slower in practice* than the standard 2-way version despite doing
asymptotically the same amount of work.

## 2. Files

| File | Purpose |
|---|---|
| `mergesort_compare.c` | C implementation of both the standard 2-way merge sort and the modified 3-way merge sort, with a benchmark harness |
| `plot_results.py` | Reads `results.csv` and produces `mergesort_growth_comparison.png` |
| `results.csv` | Benchmark output (input size, time, and comparison counts for both algorithms) — generated by running the C program |
| `mergesort_growth_comparison.png` | The resulting order-of-growth plots |
| `mergesort_compare` | Compiled binary (optional, produced by `gcc`) |

## 3. How the benchmark works

`mergesort_compare.c`:

1. Implements `mergeSort2` (standard, halves) and `mergeSort3` (modified,
   thirds), each instrumented to count the number of key comparisons
   performed.
2. For a range of input sizes `n` (1,000 up to 1,000,000), generates a
   random array, makes two identical copies, and sorts one copy with each
   algorithm.
3. Averages wall-clock time and comparison counts over 5 random trials per
   size (to reduce timing noise).
4. Verifies both outputs are correctly sorted.
5. Writes everything to `results.csv`.

## 4. How to reproduce

```bash
# 1. Compile
gcc -O2 -o mergesort_compare mergesort_compare.c

# 2. Run the benchmark (writes results.csv, takes a few seconds)
./mergesort_compare

# 3. Plot the results (requires: pip install matplotlib pandas numpy)
python3 plot_results.py
```

This produces `mergesort_growth_comparison.png`, a 2×2 figure:

1. **Running time vs n (linear axes)** — both curves overlap almost
   perfectly, showing that the two algorithms have the same order of
   growth in practice.
2. **Comparisons vs n**, with scaled `n·log₂(n)` reference curves overlaid
   — both empirical curves track an `n log n` reference curve, and the
   3-way version consistently sits above the 2-way version (larger
   constant factor).
3. **Running time vs n (log-log axes)** — both lines are straight with a
   slope of essentially 1 up to the log factor, which is the classic
   signature of `Θ(n log n)` growth (a polynomial like `n^1.5` or `n^2`
   would show a visibly steeper slope on a log-log plot).
4. **Comparisons / n vs n (semi-log x-axis)** — both curves are close to
   straight lines against `log(n)`, confirming that `comparisons(n)/n`
   grows like `log n`, i.e. `comparisons(n) = Θ(n log n)`.

## 5. Sample results

From a representative run (`results.csv`):

| n | time 2-way (s) | comparisons 2-way | time 3-way (s) | comparisons 3-way |
|---:|---:|---:|---:|---:|
| 1,000 | 0.000099 | 8,698 | 0.000094 | 10,742 |
| 32,000 | 0.004036 | 438,514 | 0.003956 | 547,020 |
| 256,000 | 0.036783 | 4,276,536 | 0.036821 | 5,344,628 |
| 1,000,000 | 0.159338 | 18,674,521 | 0.159092 | 23,352,935 |

The 3-way version consistently performs about **25% more comparisons**
than the 2-way version (matching the theoretical constant-factor
difference between the two merge strategies), yet the measured running
times track each other closely and both scale as `Θ(n log n)`, exactly as
predicted by the Master theorem analysis above.
